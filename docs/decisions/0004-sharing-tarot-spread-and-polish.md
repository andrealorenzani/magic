## 1. `noaudit`

- `Request::noAudit(array $q): bool` returns `isset($q['noaudit'])`. `$q` is already filtered to plain strings (`array_filter($_GET, 'is_string')`), so `noaudit[]=1` does not count and the request is audited as usual. The value is ignored: `?noaudit`, `?noaudit=1` and `?noaudit=` all work.
- `public/index.php`: `$noAudit = Request::noAudit($q)`; the audit block becomes `if ($view !== null && !$noAudit)`. Nothing else changes: the page is rendered, flushed and no `AuditRecord`/`AuditLog` call is made (so no config read, no connection, no log line).
- The gate keeps the parameter in its hidden `next` field (it is part of the sanitised query), so accepting the Terms and landing on the result still has no audit record.
- Forms re-submitted from a result page keep `noaudit` (a hidden field next to the existing `on` field in `templates/home.php`), so a tester does not lose it by pressing the button.
- It is not a security control: anyone can add it. The audit is an owner-side record, not an access control.

## 4. Tarot spread

### Behaviour

- Three cards, positions **Past** ("what shaped things"), **Present** ("what is happening now"), **Future** ("what is coming"), read for *the couple's connection* in Love mode. The page shows, per position: the position title and question, the card art (reversed cards drawn upside down as today), the card name, Upright/Reversed, and the position-specific text.
- The spread stays deterministic: the same people and the same reading day give the same three distinct cards and orientations, as today. The 3-day layout and per-card dates disappear.
- **Self mode has no tarot** (the Self form has no loved person and the request was for the couple's connection). Self still gets the Share section. Adding a "personal" spread to Self is an open decision, not part of this ADR.

### Content volume and layout (realistic)

22 cards x 3 positions x 2 orientations = **132 strings**, each one sentence of 80-200 characters (about 20 KB). Plus 3 position intros (title, question, one-line intro). The existing 44 generic strings in `TarotDeck::CARDS` (`upright`, `reversed`) stay as the card's short "essence" line (used as a caption under the card name) so nothing already written is wasted.

Layout: three files of 44 strings each, so authoring and review are by position and no file is unwieldy:

```
src/Content/TarotSpread.php   POSITIONS (past|present|future => title, question, intro) and text(string $cardId, string $position, bool $reversed): string
src/Content/TarotPast.php     const TEXT = [ '<card-id>' => ['up' => '...', 'rev' => '...'], ... ]   22 entries
src/Content/TarotPresent.php  same shape, 22 entries
src/Content/TarotFuture.php   same shape, 22 entries
```

`TarotSpread::text` is the only reader; a missing key throws (a test makes that impossible to ship). The writing brief for the implementer: second person plural ("you two", "between you"), one idea per sentence, no promises or medical/legal/financial advice, past = what shaped the bond, present = the current mood of it, future = a direction or invitation, reversed = the shadow or blocked version of the same card. The copy writer drafts the 132 strings; the owner reviews them.

### Code

- `Tarot\Reading::spread(string $seed, string $today): list<array{position:string, card:array, reversed:bool, text:string}>` — pure, three distinct cards. The old `draw()` is removed (single caller) and `tests/cases/tarot.php` is rewritten.
- `Tarot\Reading::fromCode(?string $code): ?list<array{number:int, reversed:bool}>` re-exported through `Share\ShareLink::parseTarot` (below): turns validated slots into the same shape as `spread()` output (texts looked up, nothing computed).
- `LoveReading::build(array $a, array $b, string $today, ?array $tarotSlots = null)`: when `$tarotSlots` is given (a validated shared spread) it is used instead of the deterministic draw; the view's `'tarot'` is the spread and gains `'tarotShared' => bool`.
- Audit: `AuditRecord::fromLove` writes `tarot` as a list of `{position, card, reversed}` (the `date` key goes away). `FORMAT_VERSION` becomes 2 (the column already exists; old rows stay readable by version). `tests/cases/audit.php` goldens are updated.

## 5. Sharing

### What is shareable (the rule)

Everything displayed that is not purely derived from the input must be in the shared URL. Classification:

| Item | Derived from input? | In the URL |
|---|---|---|
| Names, dates, times, places (lat, lon, tz, city label) | it is the input | yes |
| Signs, planets, affinities, synchrony, name affinity | yes | no (recomputed) |
| "Reading day" (biorhythm values, curves, the day the spread is for) | no, it comes from the clock | yes: `on=` |
| Tarot cards and orientation (Love) | no (a spread is a result that must stay identical) | yes: `t=` |

Self therefore encodes only input + `on`. Love encodes input + `on` + `t`.

### URL parameters

Self: `mode=self&date=YYYY-MM-DD&time=HH:MM&city=<label>&lat=<5dp>&lon=<5dp>&tz=<IANA>&on=YYYY-MM-DD&noaudit`

Love: `mode=love&a_name&a_date&a_time&a_city&a_lat&a_lon&a_tz&b_name&b_date&b_time&b_city&b_lat&b_lon&b_tz&on=YYYY-MM-DD&t=<spread>&noaudit` (only the person fields that exist are emitted).

- `t` = three comma-separated slots, Past, Present, Future: `<number><o>` with number 0-21 (no leading zero required, one or two digits) and `o` = `u` upright or `r` reversed. Example: `t=16u,5r,9u`. Regex `^(\d{1,2})([ur]),(\d{1,2})([ur]),(\d{1,2})([ur])$`, numbers 0-21, all three numbers distinct. Any other value: the **whole** `t` is ignored, the deterministic spread is drawn, and a note is shown ("The cards in this link were not valid, so a fresh reading is shown."). `t` in Self mode is silently ignored. Only plain strings are accepted (arrays are dropped by the existing filter).
- All other parameters go through the existing `Request::parse` / `parseLove` validation unchanged (bad values give the existing error messages, never a crash). Unknown parameters are ignored.
- **Coordinates are rounded to 5 decimals at parse time** (`Request`) so the sender and the recipient compute from identical numbers; the link carries the same 5 decimals.
- The link is built **from the validated model, never by echoing the raw query**: a canonical, fixed key order; values percent-encoded (`rawurlencode`, then `/`, `:` and `,` restored for readability); the city label is trimmed so its encoded form is at most 48 bytes.
- `on` is always emitted in the frozen link (see "Today").

### Today and shared links

The share section offers two links built from the same model:

1. **Link to this exact reading** (primary, also the QR): contains `on=<reading day>` and, in Love, `t=`. Opens to the same biorhythm values and the same cards.
2. **Link to a live reading**: same people, no `on`, no `t`: shows today's values and the deterministic spread for the day. Plain text link, no QR.

When a page is shown with an `on` that differs from the real UTC date, a one-line note appears above the result: "This reading is fixed to <date>." with a link to the live version. `on` keeps its current validation (1900-2100); an invalid `on` means the real date.

### Terms of use and the audit for shared links

- **The shared link never bypasses the Terms gate.** The gate already preserves the query through `Consent::safeQuery` and redirects to the result after acceptance; this stays and is covered by tests (long Love share URL, `t`, `noaudit`, `on`). The query limit in `safeQuery` (2000 bytes) is above the share limits below, so a shared link cannot be silently dropped.
- **Audit: recommendation = shared links carry `noaudit`** (one mechanism). The original request already recorded these people; the recipient opening the link would otherwise create a duplicate record of the same personal data (including the loved person's). A `shared` marker (an extra column such as `source`, migration 002, duplicate rows flagged) was considered and not recommended: it stores the same personal data again and needs a schema change. Trade-off accepted: a recipient who edits a shared link keeps `noaudit` and is not recorded; the audit is an owner-side record, not a control. **Open decision for the owner** (see summary): if opens of shared links should be counted, switch to the `shared` marker (migration + `AuditRecord` field).

### QR code (`src/Share/Qr.php`, pure)

- Standard QR Code (ISO/IEC 18004), **byte mode, error-correction level L, versions 1-15, all 8 masks evaluated**, quiet zone 4 modules. L is chosen because the code is displayed on a screen or printed clean, and it maximises capacity.
- Capacity (bytes, level L): v1 17, v2 32, v3 53, v4 78, v5 106, v6 134, v7 154, v8 192, v9 230, v10 271, v11 321, v12 367, v13 425, v14 458, v15 520. Size = 17 + 4 x version modules.
- **Maximum URL for a QR: 520 bytes (absolute URL, i.e. version 15).** Worked budget for the worst realistic Love URL (two 40-character ASCII names, 48-byte city labels, 32-byte time zones, 5-decimal coordinates, `on`, `t`, `noaudit`): about 500 bytes of query plus the site origin, so the longest realistic case needs version 14-15; a typical case (short names) is 280-340 bytes, version 10-11. Names with many non-ASCII characters can exceed the limit.
- If the absolute URL is longer than 520 bytes (or `Qr::encode` returns null), **no QR is shown**, the link is still shown, with the sentence "This link is too long for a QR code." The link itself is accepted up to the 2000-byte query limit already enforced by `Consent::safeQuery`.
- API:

```php
Qr::encode(string $data): ?array   // list<list<bool>> modules (true = dark), null if > 520 bytes
Qr::path(array $modules): string   // SVG path data for the dark modules (digits, letters and spaces only)
Qr::capacity(int $version): int    // bytes at level L, 1..15
```

- Rendering: `templates/partials/qr.php` defines `qr_svg(array $modules, string $label)` in the style of `bio_svg`: `<svg viewBox="0 0 N N" role="img" aria-label="QR code of the link above" shape-rendering="crispEdges">`, a white `<rect>` and one black `<path d="...">`; every value goes through `e()`; colours are presentation attributes (no `style=`, CSP safe). Sized by a CSS class (max 320 px), black on white in the dark theme, printed with the page.
- Nothing is sent to a third party: the QR is generated in the server process; no image file is written.

### Origin of the absolute link (I/O stays in `public/`)

`public/index.php` computes `$origin` once: scheme from `HTTPS` (or `X-Forwarded-Proto: https`), host from `HTTP_HOST` only if it matches `^[A-Za-z0-9.-]+(:[0-9]{1,5})?$`, directory of `SCRIPT_NAME`; if anything is odd, it falls back to a relative link and no QR. A hostile `Host` header only changes the link shown to the sender of that very request.

### Share section (`templates/partials/share.php`, included at the end of `self-result.php` and `love-result.php`)

- Heading "Share this reading"; read-only text input (labelled) with the frozen link; the "live" link; the QR (or the too-long sentence); a privacy sentence: "The link contains the names and birth details you entered. Share it only with people you trust."
- `public/assets/share.js` (progressive enhancement, no inline script): un-hides a "Copy link" button (`navigator.clipboard`, falling back to selecting the input) and a "Share..." button when `navigator.share` exists; both are `hidden` in the markup, like the Print button. The section works without JS.
- Print: the QR and link print with the page; the buttons are `no-print`.

### Pure link builder (`src/Share/ShareLink.php`)

```php

ShareLink::love(array $a, array $b, ?array $tarot, string $today): string
ShareLink::live(array $model...): string                                   // same without on/t
ShareLink::tarotCode(array $spread): string                                // "16u,5r,9u"

const MAX_URL_FOR_QR = 520;
```

## 6. Terms popup ("not working very well")

The shell was not available in this session, so **the docker page could not be queried with curl**; everything below is from reading `templates/home.php`, `public/consent.php`, `src/Consent.php`, `public/.htaccess` and `styles.css`. The implementer must reproduce each item with curl (`-c/-b` cookie jar) and in a browser before and after the fix.

### Findings and fixes

| # | Finding (from the code) | Fix |
|---|---|---|
| a | **Caching.** Cache headers (`private, no-store`) are only sent when `$submitted`. The gate page (chooser or a result URL without the cookie) is sent without cache headers, and its content differs by cookie. After accepting, Back/Forward or a heuristic cache can show the gate again. | Send `Cache-Control: private, no-store` and `Vary: Cookie` on every response of `index.php` (chooser, gate, result) and on `consent.php`. |
| b | **Content behind the popup.** `main` is `inert`, but the footer and the `#terms` section are not: a keyboard user can Tab to them behind the overlay. | Put the footer and the `#terms` section under the same inert condition (wrap main, footer and terms in one container carrying `inert aria-hidden="true"` while the gate is open), or give the gate state a class on `body`. |
| c | **Focus.** Nothing moves focus into the dialog; the accept button is the only action but a screen-reader user lands on the page start. No Escape/explanation of what happens. | `autofocus` on the accept button (static HTML, works without JS), `aria-describedby` pointing at the terms text, a visible focus ring (exists for buttons). No close button: closing without accepting is intentionally not possible; the hint says so. |
| d | **Small screens.** `.gate` is a grid with `place-items: center` and `overflow-y: auto`: when the box is taller than the viewport (small phone, landscape, zoom) the top is clipped and cannot be scrolled to. `.gate__box` has no `width` so it shrinks to content. | `.gate { align-items: start; }` with `.gate__box { margin: auto; width: min(100%, 520px); }`, use `min-height: 100dvh` fallback to `100vh`, `-webkit-overflow-scrolling: touch`, and make the accept button full width and sticky at the bottom of the box. |
| e | **Redirect.** `Location: ./?query#results` is relative to `consent.php`; correct while it sits next to `index.php`. The hidden `next` field drops the query silently when it is over 2000 bytes or has control characters. | Keep the relative target but add a test per case; log nothing; show the gate again with a visible sentence if `next` was dropped ("Your link could not be kept, please open it again after accepting."). Share URLs are far below the limit. |
| f | **Cookie Secure flag behind a proxy.** `Secure` is set only when `$_SERVER['HTTPS']` is set; behind a TLS-terminating proxy it is empty, so the cookie is sent without `Secure`. | Also treat `HTTP_X_FORWARDED_PROTO === 'https'` as secure (it can only make the cookie stricter). |
| g | **Cookies blocked.** If the browser rejects the cookie, accepting redirects to the gate again with no explanation. | Hint under the button: "Your browser must allow cookies to remember your choice." |
| h | **Withdraw.** The button is inside a closed `<details>` at the page end; after withdrawing, the visitor is sent to the plain home page, losing the result they were looking at. | After withdrawing, redirect to `./` (as now) but show the gate with the sentence "You withdrew your acceptance." only through the normal gate; the button stays where it is, and its label becomes "Withdraw my acceptance and clear the cookie". No other change (keeps the results unprocessed without consent). |
| i | **POST from another path.** `action="consent.php"` is relative; from `/index.php/x` it would resolve under that path. | Use a root-relative path computed from the same directory logic as `$origin` (a `$base` variable from `public/index.php`, empty when at the root). |
| j | **Clickjacking and form target.** The CSP has no `frame-ancestors`/`form-action`, so the accept button could be framed. | Add `frame-ancestors 'none'; form-action 'self'; base-uri 'none'` to the CSP in `public/.htaccess`. |
| k | **`aria-live` on the whole results section** makes screen readers announce the whole result. | Remove `aria-live` from `#results` (keep it only on the error notes). |

### Terms text

`templates/partials/terms.php` says "every result request is recorded". With `noaudit` shared links this must read: "every result you request is recorded ... Opening a link that someone shared with you is not recorded again." Existing consent cookies stay valid (wording only narrows what is recorded); the owner approves the new sentence.

## Proposed CLAUDE.md rule (new line)

> **Shareable state lives in the URL.** Everything the page displays that is not purely derived from the form input (the reading day, tarot cards and orientation, any future random or time-dependent choice) must be encoded in the share URL, validated on read (invalid value: ignore it and say so; never crash), and covered by a round-trip test. Anything new that a result shows must be classified as "derived" or "encoded" in the ADR.

## Alternatives considered

- **Server-stored shares (short code in MySQL):** short links and tiny QR, but stores personal data again and needs a schema/privacy decision. Rejected for now; the URL approach needs no storage.
- **Signed links (HMAC):** would let the server trust `noaudit`/`t`; needs a secret in config, which may be absent. Rejected.
- **External QR service or a JS library:** violates D1/privacy/CSP. Rejected.
- **ECC M or Q:** more robust codes but a worst case of version 20+; unnecessary for clean screens. Rejected.
- **A compact binary/base64 payload instead of readable parameters:** shorter QR, but the link stops being a normal, editable page URL and old-link compatibility (D8) is lost. Rejected.
- **Random tarot draw per click:** fits "encode the cards" best but breaks "same reading on reload"; kept deterministic, the `t` parameter works for both (open decision below if a "Draw again" button is wanted).
- **Per-card compositional texts (one card line + a generic position frame):** 30 strings instead of 132 but the position texts would be generic. Rejected in favour of the 132 real strings.
- **`shared=1` marker for the audit:** see section 5.

## Risks

- Writing 132 good tarot strings is the largest cost; quality is a content risk, not a technical one. A review pass by the owner is needed.
- The hand-written QR encoder is easy to get subtly wrong (a code that looks right but does not scan). Mitigation: structural tests, format/version information checks, and a mandatory manual scan with at least two phones for a short, a typical and a longest URL.
- QR version 15 is dense (77 modules); on small screens it may be hard to scan. The 320 px cap and the "link too long" fallback reduce the risk; long names should be avoided by users.
- Shared links carry personal data (including the loved person's); the existing warning is repeated in the Share section. Browser history and access logs see it (already true today).
- Calling `noaudit` the single mechanism means opens of shared links are invisible to the audit.
